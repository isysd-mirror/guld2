# Spec 09 — P2P

**Status:** draft (phase C — Hello + tx + block/header sync + CAS objects + hardening)  
**GIP:** [`../gips/gip-15.md`](../gips/gip-15.md)

## 1. Goals

- Discover peers (explicit dial / bootnodes; optional LAN mDNS in `--dev`)
- Gossip transactions
- Propagate blocks / headers
- Serve CAS objects on request
- Enforce DoS limits and ban scoring; persist known peers

## 2. Transport

**Locked:** [libp2p](https://libp2p.io/) over **TCP + Noise + Yamux**.

| Behaviour | Role |
|-----------|------|
| **identify** | Peer info / agent version (`guld-node/<semver>`); address learning for peerstore |
| **gossipsub** | `InvTx`, `InvBlock` announcements |
| **request-response (JSON)** | `Hello`, `GetTx` / `Tx`, `GetBlock` / `Block`, `GetHeaders` / `Headers`, `GetObjects` / `Objects` |
| **mdns** | Optional LAN discovery when `enable_mdns` (`guld-node --dev`) |

Default listen: operator sets `--p2p <ip:port>` → multiaddr `/ip4/<ip>/tcp/<port>`.  
Identity key: `datadir/keys/p2p.key` (Ed25519, libp2p encoding).  
Peerstore: `datadir/peerstore/peers.json` (known multiaddrs + banned peer ids).

**Not used for wallets:** browsers and dapps use HTTP/JSON-RPC only ([research note](../research/jsonrpc-vs-http-api.md)).

## 3. Message types (logical)

| Message | Transport | Payload |
|---------|-----------|---------|
| `Hello` | request-response | `chain_id`, `user_agent`, `best_height`, `guld_rules_hash` |
| `InvTx` | gossipsub topic `/guld/1/inv-tx` | tx id (32-byte hex) |
| `GetTx` / `Tx` | request-response `/guld/tx/1.0.0` | tx id → full tx JSON |
| `InvBlock` | gossipsub topic `/guld/1/inv-block` | block hash + height |
| `GetBlock` / `Block` | request-response `/guld/block/1.0.0` | block hash → full block JSON |
| `GetHeaders` / `Headers` | request-response `/guld/headers/1.0.0` | locator hashes → header JSON list (≤128) |
| `GetObjects` / `Objects` | request-response `/guld/objects/1.0.0` | `ObjectId[]` → `{id, data?}` (hex bytes; size-limited) |

### 3.1 Hello rules

On a new connection, either peer MAY send `Hello`. Receiver MUST reply with its own `Hello`.  
If `chain_id` mismatches, disconnect. If `guld_rules_hash` mismatches, disconnect.  
If peer `best_height` is greater than local tip, the lagging peer SHOULD request headers (sync).

### 3.2 Tx gossip rules

1. Local mempool insert → publish `InvTx(id)`; retain bytes to serve `GetTx`.
2. On `InvTx`: if unknown, `GetTx` from announcer (or any peer that advertised it).
3. On `Tx`: validate JSON decode; insert mempool; do **not** re-announce if already known.
4. Max tx JSON size: **1 MiB** (DoS).

### 3.3 Block / header sync (phase B)

1. After sealing a block → publish `InvBlock(hash, height)`; retain bytes to serve `GetBlock` / `GetHeaders`.
2. On `InvBlock`: if unknown, `GetBlock` from announcer.
3. On `Block`: validate PoW + parent link; `import_block` onto tip; persist; seed local serve store. Out-of-order blocks MAY be buffered as orphans until the parent arrives.
4. **Headers-first catch-up:** when Hello shows a higher tip, send `GetHeaders` with a locator `[local_tip_hash, genesis_hash?]`. Server walks forward from the first known locator hash and returns up to 128 headers. Client then `GetBlock` for each unknown header and imports in height order.
5. Max block JSON size: **4 MiB**.

Peers with **different genesis** (different keys / tip) will Hello but cannot sync — they share no locator. Testnets SHOULD bootstrap from one seed datadir or wait until genesis is identical.

### 3.4 CAS objects (phase C)

1. After `guld_putObject` (or successful inbound Objects), node seeds the P2P object serve store.
2. Peer MAY `GetObjects { ids }` (≤ **64** ids). Server returns known objects as `"0x" + hex(bytes)`; missing ids MAY omit `data`.
3. Receiver MUST verify `sha256(data) == id` before `cas.put`; hash mismatch ⇒ ban score.
4. Max object size: **4 MiB**; max response payload sum: **8 MiB**.

## 4. DoS limits

Peers MUST enforce:

- Max message size (1 MiB tx; 4 MiB block; 4 MiB object; gossipsub max transmit size aligned)
- Header batch cap (128)
- Object request batch cap (64) and response byte budget (8 MiB)
- Inbound RR rate limit (~128 requests / 10 s / peer); excess ⇒ score penalty
- Ban scoring: invalid payloads, hash mismatches, oversize, bad blocks; score ≥ **100** ⇒ disconnect + persist ban

## 5. Component API — `guld-p2p`

```text
P2pHandle:
  broadcast_tx / broadcast_block / seed_block / seed_object
  request_headers / request_block / request_objects
  report_misbehavior
  peer_count / subscribe(P2pEvent)
```

`P2pEvent`: `PeerHello`, `PeerAhead`, `IncomingTx`, `IncomingHeaders`, `IncomingBlock`, `IncomingObjects`, `PeerCount`, `PeerBanned`.

## 6. Node CLI

```text
guld-node --network simba --p2p ADDR [--bootnode MULTIADDR]… [--no-default-bootnodes] [--offline]
guld-node --dev --p2p ADDR   # LAN mDNS on; no guld.io defaults
```

- `--offline` — no listen, no dial; `guld_peerCount` = 0  
- **Default bootnodes:** when `--p2p` is set (and not `--dev` / `--no-default-bootnodes`), dial the published fallback list — **`https://guld.io/data/p2p-bootnodes.json`**. Compiled fallback: `/dns4/guld.io/tcp/4001`.  
- `guld_syncing` — `true` while catching up after `PeerAhead`.

## 7. Open parameters (later)

- Whether light clients use the same protocol  
- DNSaddr / signed bootnode attestations  
- QUIC / WebTransport transports
